# Интелектуальная система контроля (ИСК) — версия 0.1

FastAPI + React Router DOM v7 + Tailwind CSS v4 + SQLite. Локальное приложение для анализа данных Ozon FBO.

## Запуск и обновление Windows

1. Нужен Python 3.12 или новее с Python Launcher (https://www.python.org/downloads/windows/).
2. Остановите предыдущий сервер через Ctrl+C. Полностью распакуйте архив в новую папку.
3. Запустите start_windows.bat. При первом запуске создаётся .venv и устанавливаются зависимости с PyPI; нужен интернет. При ошибке установки повторите setup_windows.bat.
4. Откроется http://127.0.0.1:8000. Консоль должна оставаться открытой. Если браузер не открылся, откройте адрес вручную.
5. Подключите кабинет ключом чтения, обновите остатки и ОБЯЗАТЕЛЬНО ЗАГРУЗИТЕ ИСТОРИЮ ЗАНОВО: прежние версии не сохраняли склад отгрузки.
6. Откройте «Прогноз пополнения» и выберите период. Для окна 90 дней загрузите историю за 180 дней.

Frontend уже собран: для запуска не требуются Node.js и Nginx. База веб-версии сохраняется в %LOCALAPPDATA%\VKR_Ozon_FBO_Web\inventory.sqlite3, обновление её не удаляет. Ключ нужно вводить заново после перезапуска.

## Единый прогноз пополнения

Разделы «Прогноз запасов» и «Пополнение» удалены, их прежние адреса перенаправляются в новый раздел. Графики гипотетической партии, упаковки и сроков поставщика удалены. Остались выбор периода 7, 14, 30 или 90 дней и два уровня:

1. По складам: каждый SKU раскрывается в таблицу всех известных программе складов. Доступно; заказано за период; скорость в единицах/день; дней до исчерпания; дата. Пустые склады не скрываются.
2. По всему SKU: суммарный доступный запас, общий темп по всем складам и ожидаемая дата исчерпания общего запаса. Используется как ориентир для закупки у поставщика.

Три месяца в фильтре явно определены как 90 дней. Период общий для обоих уровней, пересчёт выполняется автоматически. Программа не выбирает оптимальное окно и не оценивает будущие изменения спроса.

## Расчёт

Скорость по складу = сумма количества товара в неотменённых отправлениях с этим складом отгрузки за период / количество полных календарных дней периода. Общая скорость = аналогичное количество по всем складам / дни. Не распределяем общий спрос пропорционально остаткам и не складываем средние показатели Ozon.

Учитываются статусы awaiting_packaging, awaiting_deliver, delivering, delivered по дате создания отправления. Отмены исключены. Это темп заказов, не бухгалтерские продажи; возвраты пока не учтены. Неизвестные статусы блокируют достоверный темп соответствующего SKU. Время — московское. Текущий и первый неполный день не входят, нулевые дни входят. Требуется полная история для выбранного периода.

Срок = доступный запас / скорость. Дата = время снимка остатков + срок. Общий срок = сумма доступных остатков / суммарная скорость (не среднее складских сроков).

Нулевой остаток показывается как «Нет в наличии» без придуманной даты прошлого исчерпания. При положительном остатке и нулевом темпе — «Нет заказов за период», дата не определяется. Если в API нет строки SKU/склад, показываем «Нет данных об остатке», а не 0. Склады — объединение известных из каталога остатков и истории за выбранный период; это не полный перечень всех объектов Ozon. Общий запас берётся из той же аналитики, что и в разделе остатков. Дополнительные склады из истории или исходного учёта без строки аналитики не скрывают известную сумму: выводится предупреждение о неполной детализации. Если аналитики для SKU нет совсем, запас остаётся неизвестным.

История загружается с with.analytics_data=true. Сохраняются только warehouse_id/warehouse_name, даты, статусы и товарный состав, без города покупателя и юридических сведений. Старый снимок истории распознаётся: требуется повторная загрузка. Если часть заказов SKU не привязана к складу, они входят в общий темп, но индивидуальные складские скорости и сроки считаются неизвестными.

## Ограничения модели

Первый уровень использует склад фактической отгрузки, а не регион спроса покупателя. Наличие товара на складе не гарантирует локальную доставку каждому покупателю. Изменение маршрутизации Ozon и отсутствие товара в прошлом могут менять наблюдаемую скорость. Второй уровень предполагает продажу общего запаса независимо от размещения; ограничения доставки могут нарушать это предположение.

Поступления, собственный склад продавца, будущие акции и возвраты пока не моделируются. Дата исчерпания — ориентир, не рекомендуемая дата заказа: необходимо отступить от неё на полный срок поставки. Проверяйте актуальность снимков.

## Другие разделы

Обзор; товары; остатки FBO с раскрытием карточек; история отправлений; подключение; журнал. Доступный запас берётся из available_stock_count. Исходные present/reserved доступны отдельно, число строк API не считается числом единиц.

## Безопасность и разработка

### Пользователи и сессии

- Публичной регистрации нет. Первый администратор создаётся только командой внутри контейнера; новых обычных пользователей администратор приглашает через раздел «Пользователи».
- Пароли хранятся как scrypt-хеши с индивидуальной случайной солью. После 8 неудачных попыток для пары IP/логин (и 8 попыток с одного IP) вход блокируется на 15 минут.
- Авторизация хранится в SQLite как SHA-256-хеш случайного токена. Cookie `isk_session` имеет флаги HttpOnly и SameSite=Strict, срок — 30 дней. Выход и отключение пользователя отзывают серверную сессию.
- Все защищённые API-маршруты, включая серверный поиск WB, требуют авторизацию. POST-запросы проверяют точный Origin по `ISK_ALLOWED_ORIGINS`.
- Данные кабинета привязаны к внутреннему ID учётной записи и владельцу; один и тот же Ozon Client ID у разных пользователей создаёт разные пространства данных.

### Шифрование и VPS

- API-ключи Ozon шифруются AES-256-GCM до записи в SQLite.
- JSON-содержимое снимков, дневной оцифровки и API-кэша также шифруется AES-256-GCM. Пароли и токены в открытом виде в БД не хранятся.
- Ключ шифрования хранится в Docker Secret `secrets/isk_encryption_key`, не попадает в Git и образ. **Сделайте отдельную защищённую резервную копию ключа. Если потерять или заменить его, уже зашифрованные данные восстановить нельзя.**
- SQLite размещается в отдельном Docker volume, права каталога/файла ограничены; контейнер работает не от root, с read-only root filesystem, без Linux capabilities и с no-new-privileges.
- Шифрование не защищает от компрометации самого VPS или процесса приложения во время работы. Используйте обновлённую ОС, SSH-ключи, firewall, HTTPS reverse proxy и зашифрованные резервные копии тома.

### Первый запуск на VPS

1. Создайте секретный ключ **один раз**: `sh scripts/init-secrets.sh`. Не удаляйте и не перегенерируйте этот файл при обновлениях.
2. Создайте и настройте `.env`: домен в `ISK_ALLOWED_HOSTS`, точный HTTPS-origin в `ISK_ALLOWED_ORIGINS`, `ISK_SECURE_COOKIE=true`.
3. Запустите `docker compose up -d --build`.
4. Создайте первого администратора интерактивно: `docker compose exec isk python -m backend.admin create-admin --username admin`. Пароль вводится скрыто и должен быть не короче 12 символов.
5. Войдите в ИСК и подключите Ozon. Ключ будет сохранён зашифрованным. Следующие входы и перезапуски контейнера не требуют повторного ввода ключа.

Для локальной разработки по HTTP установите `ISK_SECURE_COOKIE=false`; на VPS за HTTPS оставляйте `true`. Порт контейнера по умолчанию опубликован только на `127.0.0.1` — наружу его напрямую не выставляйте.

### Миграция существующих данных

При первом подключении кабинета новая версия переносит старые снимки, историю, дневные данные и API-кэш из пространства, ранее названного Ozon Client ID, в отдельное пространство первого владельца этого кабинета, а затем шифрует содержимое. Миграция выполняется один раз на Client ID. Перед обновлением всё равно сделайте резервную копию SQLite.

Данные калькуляторов WB/Ozon из прежнего общего localStorage переносятся в пользовательское пространство только при первом открытии калькулятора администратором. Новые данные калькуляторов разделяются по ID пользователя. При смене браузера/устройства эти данные нужно переносить штатным экспортом/импортом JSON.

Из корня для тестов: `python -m unittest discover -s tests -v`. Frontend: `cd frontend && npm ci && npm run build`.

## Единое приложение: Оцифровка + Market Calculate (ветка `feature/ozon-digitization`)

В существующее меню ИСК добавлен раздел **Калькулятор WB / Ozon** (маршрут `/market-calculator`). Внутри: **Себестоимость 1688** (отбираемые, архив, поставки), **Калькулятор WB** и **Калькулятор Ozon**. Оригинальные разделы «Оцифровка», остатки, пополнение и подключение оставлены без изменений.

### Запуск в Docker (один контейнер)

```bash
# Первый запуск. Ветка разработки нужна явно, так как основная ветка репозитория — main.
git clone -b feature/ozon-digitization https://github.com/pereyasl0v/isk_v01.git
cd isk_v01
sh scripts/init-secrets.sh
cp .env.example .env
# Обязательно отредактируйте .env: укажите свой домен, HTTPS-origin и ISK_SECURE_COOKIE=true.
docker compose up -d --build
docker compose exec isk python -m backend.admin create-admin --username admin
# Команда интерактивно запросит пароль администратора (не менее 12 символов).
```

### Обновление после следующих коммитов

```bash
git checkout feature/ozon-digitization
git pull --ff-only origin feature/ozon-digitization
docker compose up -d --build
```

Один образ содержит FastAPI, React/Vite и расчётный модуль WB; дополнительных Node.js-сервисов в runtime нет. GitHub Actions выполняет только проверки; данные не собираются в Actions. SQLite сохраняется в именованном Docker volume `isk_data` по адресу `/data/inventory.sqlite3` и **не удаляется при `docker compose up --build`**. Не используйте `docker compose down -v`, иначе удалится том с данными.

**Важно:** при обновлении уже существующего Docker volume старые данные ИСК остаются на месте. При первом подключении соответствующего Ozon Client ID они переносятся в пространство владельца и шифруются. Если база находится вне Docker volume, её нужно отдельно перенести в `/data/inventory.sqlite3`.

### Доступ из интернета

По умолчанию порт Docker доступен **только локально** (`127.0.0.1:8000`), поскольку существующая ИСК использует локальную сессию, а не полноценную публичную авторизацию. Если приложение размещается на VPS, настройте HTTPS и обратный прокси, ограничьте доступ к приложению и задайте в `.env` реальные домены для `ISK_ALLOWED_HOSTS`, origin для `ISK_ALLOWED_ORIGINS` и `ISK_SECURE_COOKIE=true`. Не публикуйте порт 8000 непосредственно без защиты.

### Калькуляторы и расширения

Данные себестоимости и сценарии WB/Ozon хранятся в **localStorage конкретного браузера**, с отдельным ключом для каждого пользователя (не в SQLite). Прежние общие ключи localStorage при первом открытии калькулятора переносятся только администратору. Выгружайте JSON-резервную копию перед сменой домена/устройства. Отдельные расширения Chrome находятся в `extension/wb-capture` и `extension/ozon-capture`: их можно установить через `chrome://extensions` → Режим разработчика → Загрузить распакованное расширение. После поиска на маркетплейсе сохраните JSON и импортируйте в соответствующую вкладку. Импорт HAR WB происходит локально в браузере без передачи HAR на сервер.

**WB API:** экспериментальный запрос к внутреннему поисковому интерфейсу может вернуть 403 с сервера. Это не официальный Seller API. В таком случае используйте браузерный импорт HAR/JSON. Цена из JSON не гарантирует фактическую цену покупателя и не определяет СПП конкурента.

**Ozon:** расчёт сравнивает три цены ТОП-10 по двум моделям *вашей потенциальной продажи* — FBO и FBS. Это **не определение фактической схемы работы конкурентов**. Расходы и ставки предварительные (пример из Ozon XLSX) и требуют проверки по категории/маршруту. Подробности в `docs/ozon-calculator-model.md`.
