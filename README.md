# Интелектуальная система контроля (ИСК) — версия 0.1

FastAPI + React Router DOM v7 + Tailwind CSS v4 + SQLite. Локальное приложение для анализа данных Ozon FBO.

## Запуск и обновление Windows

1. Нужен Python 3.12 или новее с Python Launcher (https://www.python.org/downloads/windows/).
2. Остановите предыдущий сервер через Ctrl+C. Полностью распакуйте архив в новую папку.
3. Запустите start_windows.bat. При первом запуске создаётся .venv и устанавливаются зависимости с PyPI; нужен интернет. При ошибке установки повторите setup_windows.bat.
4. Откроется http://127.0.0.1:8000. Консоль должна оставаться открытой. Если браузер не открылся, откройте адрес вручную.
5. Подключите кабинет ключом чтения, обновите остатки и ОБЯЗАТЕЛЬНО ЗАГРУЗИТЕ ИСТОРИЮ ЗАНОВО: прежние версии не сохраняли склад отгрузки.
6. Откройте «Прогноз пополнения» и выберите период. Для окна 90 дней загрузите историю за 180 дней.

Frontend уже собран: для запуска не требуются Node.js и Nginx. База веб-версии сохраняется в %LOCALAPPDATA%\VKR_Ozon_FBO_Web\inventory.sqlite3, обновление её не удаляет. Ключ нужно вводить заново после перезапуска.

## Единый прогноз пополнения

Разделы «Прогноз запасов» и «Пополнение» удалены, их прежние адреса перенаправляются в новый раздел. Графики гипотетической партии, упаковки и сроков поставщика удалены. Остались выбор периода 7, 14, 30 или 90 дней и два уровня:

1. По складам: каждый SKU раскрывается в таблицу всех известных программе складов. Доступно; заказано за период; скорость в единицах/день; дней до исчерпания; дата. Пустые склады не скрываются.
2. По всему SKU: суммарный доступный запас, общий темп по всем складам и ожидаемая дата исчерпания общего запаса. Используется как ориентир для закупки у поставщика.

Три месяца в фильтре явно определены как 90 дней. Период общий для обоих уровней, пересчёт выполняется автоматически. Программа не выбирает оптимальное окно и не оценивает будущие изменения спроса.

## Расчёт

Скорость по складу = сумма количества товара в неотменённых отправлениях с этим складом отгрузки за период / количество полных календарных дней периода. Общая скорость = аналогичное количество по всем складам / дни. Не распределяем общий спрос пропорционально остаткам и не складываем средние показатели Ozon.

Учитываются статусы awaiting_packaging, awaiting_deliver, delivering, delivered по дате создания отправления. Отмены исключены. Это темп заказов, не бухгалтерские продажи; возвраты пока не учтены. Неизвестные статусы блокируют достоверный темп соответствующего SKU. Время — московское. Текущий и первый неполный день не входят, нулевые дни входят. Требуется полная история для выбранного периода.

Срок = доступный запас / скорость. Дата = время снимка остатков + срок. Общий срок = сумма доступных остатков / суммарная скорость (не среднее складских сроков).

Нулевой остаток показывается как «Нет в наличии» без придуманной даты прошлого исчерпания. При положительном остатке и нулевом темпе — «Нет заказов за период», дата не определяется. Если в API нет строки SKU/склад, показываем «Нет данных об остатке», а не 0. Склады — объединение известных из каталога остатков и истории за выбранный период; это не полный перечень всех объектов Ozon. Общий запас берётся из той же аналитики, что и в разделе остатков. Дополнительные склады из истории или исходного учёта без строки аналитики не скрывают известную сумму: выводится предупреждение о неполной детализации. Если аналитики для SKU нет совсем, запас остаётся неизвестным.

История загружается с with.analytics_data=true. Сохраняются только warehouse_id/warehouse_name, даты, статусы и товарный состав, без города покупателя и юридических сведений. Старый снимок истории распознаётся: требуется повторная загрузка. Если часть заказов SKU не привязана к складу, они входят в общий темп, но индивидуальные складские скорости и сроки считаются неизвестными.

## Ограничения модели

Первый уровень использует склад фактической отгрузки, а не регион спроса покупателя. Наличие товара на складе не гарантирует локальную доставку каждому покупателю. Изменение маршрутизации Ozon и отсутствие товара в прошлом могут менять наблюдаемую скорость. Второй уровень предполагает продажу общего запаса независимо от размещения; ограничения доставки могут нарушать это предположение.

Поступления, собственный склад продавца, будущие акции и возвраты пока не моделируются. Дата исчерпания — ориентир, не рекомендуемая дата заказа: необходимо отступить от неё на полный срок поставки. Проверяйте актуальность снимков.

## Другие разделы

Обзор; товары; остатки FBO с раскрытием карточек; история отправлений; подключение; журнал. Доступный запас берётся из available_stock_count. Исходные present/reserved доступны отдельно, число строк API не считается числом единиц.

## Безопасность и разработка

Сервер слушает только 127.0.0.1. Ключ находится только в памяти сервера; сессия через HttpOnly SameSite cookie. Есть проверка Origin и защитного заголовка. Данные SQLite не зашифрованы. Не публикуйте эту локальную конфигурацию в интернет без отдельной аутентификации и HTTPS. Запросы к Ozon только информационные.

Из корня: python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --reload.
Frontend: Node.js 22.12+ или 24, затем в frontend: npm ci, npm run dev. Адрес http://127.0.0.1:5173. Сборка npm run build, затем перезапуск backend.
Тесты: python -m unittest discover -s tests -v. Проверка представления: node frontend/test-presentation.mjs.

Зависимости зафиксированы. В архив не включены база, ключи, node_modules и .venv. Реальная выгрузка нового поля склада требует проверки на кабинете пользователя; автоматические тесты используют синтетические данные.

Исправление расчёта: складские идентификаторы без аналитики больше не скрывают весь остаток SKU. Строки с рассчитанным сроком сортируются первыми, склады без данных последними. Для примера 226 единиц и 6 единиц/день срок равен 37,67 дня. После обновления повторная выгрузка не нужна, если ранее уже загружена история со складами.
